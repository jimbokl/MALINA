# Разбор исходного BerryVerse-бэклога

Оригинал сохранён [здесь](source/berryverse-original-2026-09-24.txt). Это сценарий продукта при гипотетических 100 разработчиках. Сохранены все 13 исходных эпиков; ниже показано, как они переходят в рабочий [BACKLOG.md](../BACKLOG.md). Цифры про точность, фото, нагрузку, капитализацию и IPO в исходном тексте не являются подтверждёнными требованиями.

| Исходный эпик | Решение | Связь с рабочим бэклогом |
| --- | --- | --- |
| 1.1 PIM и графовая база | Нужен каталог с происхождением данных; Neo4j, 500 признаков и реестровые API — после доказанной потребности и проверки доступа. | D-01–D-03, M-05, R-07 |
| 1.2 Корзина и чекаут | Сначала продавец и актуальное предложение. Разделение заказа, ML-цена и эскроу требуют реальных смешанных заказов, правил и операционной модели. | C-01–C-04, M-02, R-08 |
| 1.3 B2B-маркетплейс | Сохраняем как направление после сделок и партнёров; импорт прайсов раньше аукционов и ЭДО. | C-05, M-01, M-03, R-08 |
| 2.1 CV-диагностика | Исследование после лицензированного набора данных и экспертной оценки ошибок. «Точность >95%» без определения выборки и метрик недостаточна. Автоматический протокол лечения не принимается как готовое требование. | R-01 |
| 2.2 ИИ-подбор и урожай | Сначала прозрачные правила. Метеоданные и модели сравнивать с базой; точные килограммы и даты не обещать. | D-04, W-03, R-02–R-03 |
| 2.3 NLP и контент | ИИ может помогать редакции. Массовая автопубликация SEO-статей не заменяет полезный и проверенный материал; чат требует испытаний качества. | W-04, R-04 |
| 3.1 Мобильные приложения | Сначала мобильный веб. Офлайн, push и AR рассматриваются по отдельным сценариям и данным. | W-05, G-03, R-05 |
| 3.2 Соцсеть | Проверить повторные задачи сада и готовность модерации; журнал посадок раньше ленты, бейджей и обмена. | G-02, G-04, R-09 |
| 4.1 WMS | Имеет смысл только при собственных операциях и измеренной сложности сборки. | C-03–C-04, M-04 |
| 4.2 Agro-IoT | Нужны реальный объект, безопасность управления и агрономический смысл данных. Телеметрия на главной не является пользовательской ценностью сама по себе. | R-06 |
| 5.1 Highload и микросервисы | Спроектировать границы модулей сейчас; Kafka/Kubernetes/сервисы после измеренных ограничений и расчёта эксплуатации. | F-04–F-05, R-07 |
| 5.2 WASM и Edge | Содержательный HTML, скорость и интерактивность нужны сразу. Свой UI-фреймворк, 3D и «<50 мс» не являются входным критерием. | W-01–W-05, R-09 |
| 5.3 Data Lake | Нужны определения событий и решения, для которых они собираются; ClickHouse/Superset после реального объёма. | F-06, R-07 |

## Главные изменения относительно оригинала

1. Вместо распределения гипотетических 100 человек появился порядок по пользовательской ценности, данным и зависимостям.
2. Вместо заранее выбранного набора технологий — архитектурное решение с условиями пересмотра.
3. Вместо обещаний точной диагностики и урожая — проверяемые правила, оценки ошибок и ограничений.
4. Вместо единого маркетплейса «на словах» — раздельные модели сорта, продавца, предложения, остатка и заказа.
5. Дальние идеи сохранены в резерве, чтобы масштаб не потерялся, но не мешал первому выпуску.
