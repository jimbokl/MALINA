## Вертикальные срезы

Первый кодовый срез после F-04: одна опубликованная карточка сорта с источником → страница → проверка на мобильном устройстве → редакторское исправление. Следующий: ввод условий → объяснимое правило → карточка. Такой порядок проверяет данные, интерфейс, публикацию и эксплуатацию раньше, чем расширение каталога.

## Definition of Ready для задачи

- Указан ID из `BACKLOG.md`, пользовательский сценарий, владелец решения и проверяемый результат.
- Известны необходимые данные, права и зависимости; блокеры названы.
- Для изменения публичного факта есть источник и редакторский критерий.
- Для изменения технического контракта определены вход, выход, ошибки и обратная совместимость.

## Definition of Done для изменения

- Реализован сценарий и проверены ошибки, пустые состояния и права доступа.
- Пройдены релевантные автоматические проверки; ручная проверка записана там, где она необходима.
- Для публичного интерфейса проверены мобильный размер, клавиатура, читаемость, содержательный HTML и скорость на реальном окружении.
- Для данных проверены источник, лицензия, версия и возможность исправления/удаления.
- Для интеграций проверены повторные запросы, таймауты, наблюдаемость и безопасная деградация.
- Обновлены документация, миграции/контракты и состояние задачи; секреты не попали в репозиторий.

## Проверки по мере появления кода

1. При каждом изменении: форматирование, статический анализ/типизация, сборка и тесты логики, которую можно сломать.
2. Для данных: проверка схемы, дубликатов сортов, обязательных источников и лицензий, ручная редакторская выборка.
3. Для основных пользовательских путей: сценарии браузера от входа на сайт до результата подбора и предложения, включая отсутствие предложения.
4. Перед публикацией: мобильная проверка, доступность, скорость, ошибки сервера, резервное копирование и восстановление данных.
5. После публикации: мониторинг ошибок, индексации, качества предложений и исправлений. Измерять сначала базовый уровень, затем ставить бюджет и цель.

До настройки CI эти проверки — требования к будущему контуру разработки, а не якобы выполненные тесты.

## Работа нескольких команд

Параллельные потоки возможны по стабильным контрактам: данные/редактура, публичный веб, коммерция, инфраструктура, исследование. Нужны владельцы модулей и единый процесс интеграции. Численность из исходного текста не определяет структуру команды автоматически. Общие схемы и пользовательские сценарии согласуются до разделения задач между потоками.

## Первый релиз: минимальная проверка

Показать работающий путь реальному садоводу, проверить понятность объяснения выбора и исправить обнаруженные ошибки. Публикация сайта требует отдельной проверки домена, материалов, условий использования, безопасности и фактического продавца, если есть коммерческие кнопки.
