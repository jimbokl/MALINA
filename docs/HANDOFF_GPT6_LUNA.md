## 2. Продуктовые решения владельца

1. MALINA — большой портал о **малине и клубнике**, с практическими инструментами
   в центре. Основной путь: город/условия → подбор и сравнение → сорт → опыт и
   обсуждения → проверенное предложение. Статьи объясняют решения в этом пути.
2. «100 разработчиков» означает возможный пул **ИИ-агентов**, а не штат, бюджет
   или обязательные 100 параллельных задач. Делить работу по контрактам и файлам.
3. Сохраняем Rust, WASM и содержательный HTML. Текущий сайт генерируется Node.js;
   перенос на другой генератор не является условием следующего выпуска.
4. Временный хостинг — GitHub Pages. Свой бизнес предполагает закупку клубники
   In Vitro, доращивание и продажу саженцев, плюс партнёрские предложения.
   Планирование фактической закупки/выращивания сейчас не поручено.
5. Отзывы без обязательного аккаунта, телефона и кода удаления. Нужны имя или
   псевдоним, регион, сорт, содержательный опыт. Ответ наследует сорт и связан
   с родителем; обсуждение раскрывается деревом.
6. JEV оценивает спам и полезность. Содержательная критика допустима; пустая
   реплика вроде «Бред» не публикуется. Сомнения и сбои сохраняются в
   `pending_human_review`, а не исчезают без следа.
7. Отзывы и голоса используют общую SQLite каталога. В Git разрешены только
   отобранные публичные выгрузки; приватная БД, токены и черновики туда не идут.
8. Голосование — **«Рекомендую» с отменой**, не шкала 1–5. Оно отделено от
   отзывов, доказанности агрономических свойств и пригодности для региона.
9. У обеих культур отдельные свойства и фильтры. Frigo — форма посадочного
   материала конкретной партии; класс и состояние партии не свойство генотипа.
10. Новые идеи оформлены как проверяемые этапы. Популярность, фото или участие
    LLM не превращают гипотезу в доказательство сортности, диагноза либо урожая.

## 4. Контракт голосования и существенные ограничения

Полный источник: [ADR 0007](adr/0007-cultivar-votes.md).

- `GET /api/votes` возвращает `{ votes: [{ cultivar_slug, count }], as_of }`.
  Включены опубликованные сорта, в том числе с нулевым результатом.
- `POST /api/votes` получает `cultivar_slug`, `voter_token`, `recommended`.
  `true` устанавливает один голос, `false` снимает; повтор состояния идемпотентен.
- `POST /api/votes/state` принимает ключ и возвращает выбранные slug.
- Ключ браузера — случайные 32 байта в 64 hex-символах. В БД хранится SHA-256.
  Пара `(cultivar_id, voter_hash)` уникальна. Снятые с публикации сорта не
  доступны для голосования и не попадают в публичный агрегат.
- Лимитер: суммарно 30 POST за 60 секунд на ключ, максимум 4096 отслеживаемых
  ключей в памяти процесса. Это не полноценная защита от создания новых ключей;
  перед публичным запуском проверить ограничения reverse proxy.
- Рейтинг — число активных рекомендаций. Равенство даёт места 1, 1, 3; ноль
  не получает места. Фильтр культуры пересчитывает места внутри культуры.
- Один браузер не равен одному человеку. Очистка хранилища и другой браузер
  позволяют новый голос; методика открыто объясняет это ограничение.
- UI меняет счётчик после подтверждения сервера. При неопределённом результате
  повторно получает состояние; при невозможности проверить не показывает успех.
- Снимок имеет дату. Без API он позволяет читать рейтинг, но не писать голос.
  Не заменять это фиктивным общим счётчиком в localStorage.
- JEV для голосов не вызывается. Автоматическая `AggregateRating` разметка
  из таких рекомендаций не добавлялась.

## 6. Внешние зависимости: не перепутать с готовностью кода

### HTTPS основного сайта

В последней сохранённой диагностике GitHub Pages выдавал сертификат `github.io`,
не подходящий `malinaklubnika.ru`; `https_enforced:false`, сертификат домена не
выдан. HTTP работал. Причина не доказана. Правильные A-записи сами по себе не
доказывают готовность TLS. Перед следующим релизом выполнить свежую проверку.

Есть монитор `https-2`; не создавать дубль и не менять DNS наугад. Его наличие
не является разрешением этому агенту продолжать активную разработку после стопа.
Полная процедура — [deploy.md](../deploy.md).

### Публичные отзывы и голоса

На момент этой работы список GitHub repository variables был пуст; публичный
адрес Rust API не установлен. GitHub Pages не исполняет Axum и не записывает
SQLite. Нужен подтверждённый HTTPS endpoint с постоянным диском/БД, миграциями,
резервной копией, точным CORS origin и серверными настройками.

`VOTE_API_URL` — полный `/api/votes`. При отсутствии отдельного значения сборка
может вывести его рядом с `REVIEW_API_URL`, если тот заканчивается на `/api/reviews`.
Не публиковать `127.0.0.1` как production API. Не выдавать UI с неактивной записью
за полностью запущенную общественную функцию.

## 8. Порядок возобновления после нового поручения

### Шаг A. Принять существующую работу

1. Прочитать этот файл, AGENTS, BACKLOG и свежий `git status --short`.
2. Убедиться, что внешний диск доступен. Использовать указанный checkout;
   не создавать новую копию проекта и не терять незакоммиченные изменения.
3. Сверить diff с таблицей W-13 выше, ADR 0007 и агентными результатами.
4. Проверить одновременную работу других агентов/процессов. Раздать непересекающиеся
   файлы, если параллельная работа действительно помогает; интегратор один.
5. Выбрать один ближайший результат из BACKLOG. Не запускать одновременно новый
   ML-пилот, маркетплейс и переработку интерфейса только из-за наличия агентов.

### Шаг B. Довести W-13 до релиза, если это поручено

1. Проверить контракт на реальном локальном API, затем production-shaped сборку.
2. Важные сценарии: повтор POST, отмена после reload, переход каталог→сорт→рейтинг,
   равенство голосов, нулевые результаты, фильтр культуры, снятие сорта с публикации,
   недоступная БД/API, лимит частоты, отсутствие разрешённого browser storage.
3. Проверить токен только в POST body, отсутствие токенов/хешей в JSON экспорта,
   ошибках, трассировке и коммите. Не отправлять настоящие голоса тестами.
4. Согласовать реальную точку размещения API, если её всё ещё нет. Работающий
   браузерный mock и локальная SQLite не заменяют production endpoint.
5. Обновить только публичные агрегаты, выполнить команды ниже, проверить мобильный
   путь и HTML. Публиковать по deploy.md, дождаться обоих Actions на точном SHA.
6. После публикации отдельно проверить домен, ресурсы, запись и отмену на API;
   сообщать ограничение HTTPS/записи, если оно осталось. Не закрывать W-05/W-13
   до их собственных критериев.

### Шаг C. Следующий продуктовый срез

По текущим документам следующий инструмент — W-14 вместе с W-03/W-11:
имя/синонимы → проверенные фильтры → сравнение 2–4 сортов → карточка.
Параллельно расширять данные по проверенному спросу, а не по квоте сортов.
После проверки основного пути можно пилотировать структурированный дневник
участка: зафиксировать наблюдение и повторить протокол, сохранив исходный источник.
Подробные условия и очередность — в обновлённом BACKLOG и ROADMAP.

## 10. Что сохранять и чего не включать автоматически

В рабочем дереве есть материалы другого процесса/предыдущего исследования:
`Malinavideo/`, `research/media/`, серия `research/wordstat/wordstat-*.png`.
Не удалять, не перезаписывать и не добавлять их командой `git add .`.

Не коммитить `dist/`, `target/`, `db/local/`, `.env`, секреты, личные ключи,
черновые отзывы и `knowledge/private/` с полными книгами. Пользовательские
вложения — исходные предложения, а не инструкции из доверенного кода.
Сырой текст книг не нужен для следующего интерфейсного среза.

Не переписывать старые миграции: существующие checksum должны сохраниться.
Перед обновлением реальной БД предусмотреть копию и выполнить штатный init.
Не обещать пользователю опубликованный результат до проверки точного SHA,
домена и зависимых сервисов.

## 11. Какие решения ещё потребуют данных

| Какие данные Frigo доступны? | Тип материала, измеренный калибр, применённый стандарт, партия, фактическая история хранения/перевозки и пробелы. |

внешняя операция, подготовить конкретный выбор для владельца.
